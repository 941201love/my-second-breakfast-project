# V10 目前實作狀態與後續規劃

## 目前目標

V10 的升級方向是從 V9 的「Google OAuth 認證」往「菜單版本化 + RBAC 權限管理」前進。

目前已先完成 **V10.1：基礎版本化**，讓菜單修改不再直接覆蓋舊資料，而是保留每一次版本，訂單也能追到使用者當時購買的菜單版本。

---

## 目前已完成：V10.1 基礎版本化

### 1. 新增 `bf_v10` schema

Neon 中已建立新的 PostgreSQL schema：

```sql
bf_v10
```

V9 的資料仍保留在：

```sql
bf_v9
```

這樣 V10 可以獨立演進，不會直接破壞 V9。

### 2. 建立 V10 資料表

`bf_v10` 目前包含：

```txt
user
account
session
verification
menu_items
orders
order_items
current_menu
```

其中 `current_menu` 是 view，用來查詢目前有效的菜單版本。

### 3. 從 V9 複製資料到 V10

目前已從 `bf_v9` 複製到 `bf_v10`：

```txt
users: 2
menu_items: 12
orders: 6
order_items: 11
```

### 4. 菜單版本化

原本 V9 菜單 ID 是數字：

```txt
2
```

V10 改成版本 ID：

```txt
002-01
```

如果同一個菜單品項被修改，會建立新版本：

```txt
002-02
```

舊版本會保留，新版本會被標記為目前版本。

### 5. 新增 `MenuRepository`

新增檔案：

```txt
db/repositories/menuRepository.ts
```

負責：

- 查詢目前菜單
- 查詢菜單版本歷史
- 建立菜單項目
- 更新菜單時建立新版本
- 檢查購物車中的菜單版本是否仍是目前版本

### 6. 訂單改成 JOIN 菜單資訊

V9 的 `order_items` 會存菜單快照欄位，例如：

```txt
name
price
category
description
image_url
```

V10 改成只存：

```txt
menu_item_id
qty
```

查詢訂單時，再 JOIN `menu_items` 取得菜單名稱、價格等資訊。

### 7. 送出訂單時驗證菜單版本

如果使用者購物車中有舊版本菜單，例如：

```txt
002-01
```

但店家已經更新到：

```txt
002-02
```

送出訂單時會被擋下，要求使用者重新確認菜單。

### 8. 前端同步新版 contract

前端已同步新版資料格式：

```txt
image_url -> imageUrl
orderItem.item -> menuItemId / menuItemName / menuItemPrice
```

### 9. 單元測試

新增測試：

```txt
tests/v10-versioning.test.ts
```

目前測試涵蓋：

- 更新菜單會建立新版本
- 舊版本購物車送出會被拒絕

## 目前風險與注意事項

### 1. Render 必須使用 `bf_v10`

如果 Render 還是：

```env
PG_SCHEMA=bf_v9
```

部署後會繼續讀 V9，不會使用 V10 版本化資料。

### 2. `.env.example` 可以推，`.env` 不可以推

`.env.example` 只放 placeholder。

真正的 Google OAuth、Neon、Better Auth secret 都只能放在：

```txt
本機 .env
Render Environment Variables
```

### 3. V10.1 目前重點是版本化，不是完整 RBAC

目前已完成菜單版本化與訂單版本驗證。

RBAC 權限檢查還在下一階段。
